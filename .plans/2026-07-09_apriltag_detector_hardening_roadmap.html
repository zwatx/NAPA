Execution phases

Phase 0 — owner and hardware prerequisites

  1. #7: the reviewed initial baseline now exists at 9a345a8. Choose a license, author/project metadata, repository remote, and release policy before publishing it.
  2. #2: identify the exact Pi, OS, camera, lens, resolution, exposure strategy, and robot mount. Calibrate that assembly and import the official season layout instead of editing bundled examples in place.
  3. Save production values in a new explicit deployment profile; retain laptop/raspi examples for development and make example status machine-readable.

Gate: no package publication or robot localization test until license and production profile inputs exist.

Phase 1 — evidence before concurrency

  1. #9 complete: use northstar-simulate for deterministic software regression on every supported OpenCV/Python lane. Keep generated truth separate from the strict replay manifest and label every report as synthetic evidence.
  2. #5: capture a versioned corpus spanning tag distances, angles, motion blur, partial occlusion, glare, dim scenes, duplicate/unknown tags, blank frames, camera interruptions, and multi-tag views.
  3. Add a replay benchmark that records detection recall, false positives, p50/p95/p99 processing time, end-to-end frame age, pose residuals, and memory growth. Store summarized fixtures or download instructions rather than large raw logs in the package.
  4. #8: run a local NT server/robot-side subscriber harness and record publisher-to-consumer timestamp error, disconnect behavior, backlog depth, and recovery under induced packet loss.

Gate: the synthetic report must pass before hardware work, then a separate captured baseline must run in one command on laptop and Pi. Neither lane makes a claim from a single average latency.

Phase 2 — bounded real-time boundaries

  1. #1: give one worker exclusive ownership of the camera. Replace frames atomically in a size-one slot; count overwritten frames; reconnect with bounded backoff; publish actual negotiated backend, resolution, FPS, and format.
  2. Keep all OpenCV capture operations on that worker, propagate capture wall/monotonic timestamps together, and make shutdown idempotent even during reconnect.
  3. #4: give JSONL one bounded queue and writer. Define drop-old/drop-new behavior, rotate by size or time, cap retention, and expose queue depth, drops, write latency, and last error.
  4. Resolve #8 queue semantics from Phase 1 evidence: retain upstream sendAll only if the measured robot contract requires every frame and the queue remains bounded; otherwise choose latest-value delivery explicitly.

Gate: a camera stall, disk stall, or network stall cannot grow memory or make processed frame age increase without bound.

Phase 3 — pose trust and time alignment

  1. #3: add per-tag residuals, duplicate-ID handling, iterative/RANSAC outlier removal for multi-tag solves, configured field/height bounds, and rejection reasons. Keep raw image observations available even when a field pose is rejected.
  2. Validate official artwork corner order with captured tags and preserve the golden real-detector test. Compare estimated camera poses against surveyed ground truth at multiple distances and viewing angles.
  3. #6: subscribe to robot yaw with source timestamps, keep a short interpolation buffer, sample at frame capture time, report age, and suppress trig localization when yaw is stale or outside the buffer.
  4. Turn confidence from an informal scalar into a documented quality model or remove it from decision-making until it is calibrated against observed error.

Gate: accepted poses stay inside configured physical bounds, corrupted-tag tests reject safely, and replayed pose error meets the team-selected percentile budget.

Phase 4 — release candidate

  1. Run an eight-hour Pi soak with camera, NT server, and bounded recording enabled; capture thermals, RSS memory, frame-age percentiles, reconnects, dropped frames, queue high-water marks, and disk growth.
  2. Run the full Python 3.11–3.14 CI matrix, OpenCV 4.7 floor, current OpenCV, wheel/sdist smoke installs, real NT integration test, and replay corpus gate.
  3. Freeze profile/schema/output versions, document upgrade compatibility, rebuild distributions from the committed tag, and publish only after issue #7 is complete.

Risks & mitigations

RiskLikelihoodMitigation
Threaded capture introduces shutdown racesmediumSingle camera owner, explicit state machine, fault-injection tests, idempotent close, bounded joins.
Optimization improves laptop numbers but harms Pi recallhighFull-frame remains reference; require per-bucket replay parity and Pi percentile evidence.
Renderer and solver share a convention bugmediumHard-coded ordered-corner golden test, actual OpenCV detector, explicit 180° mapping rule, then physical artwork validation.
Outlier rejection hides layout/calibration errorsmediumPublish rejection reasons and residuals; validate surveyed ground truth before tuning thresholds.
Dropping NT updates violates robot consumer assumptionsmediumDecide from a live consumer test and version the wire behavior; do not change silently.
Recorder queue protects latency but loses diagnosticsmediumDocument drop policy, expose counters, preserve a bounded pre/post-fault window where feasible.
Unlicensed or uncommitted artifact is publishedlowMake license, clean committed tree, tag, and artifact provenance explicit release gates.

Definition of done

  • Issues #1–#8 are closed with evidence, not just code presence; this plan is marked done against the release commit.
  • The target architecture has no unbounded queue, no cross-thread camera ownership, and no output I/O on the capture/processing critical path.
  • A checked-in benchmark definition and reproducible corpus manifest show detection, pose, timing, and resource percentiles on the chosen Raspberry Pi.
  • The simulator remains deterministic across supported OpenCV floors, exports replayable evidence, and never labels synthetic results as hardware validation.
  • Robot-side live testing proves timestamp interpretation, disconnect recovery, and chosen queue semantics.
  • Production calibration/layout/profile provenance is documented and examples cannot be mistaken for competition measurements.
  • The tagged wheel and sdist are built by CI from a licensed, committed tree and install cleanly in fresh environments.

Open owner decisions

  • License, author/maintainer metadata, and whether 0.3.0 remains private alpha or becomes a public release.
  • Raspberry Pi model, 64-bit OS image, camera/lens, V4L2 pixel format, exposure strategy, and exact mount.
  • Competition field/layout source and the acceptable surveyed pose-error percentiles.
  • Whether the robot needs every NT observation or always prefers the newest bounded-latency pose.

The reusable Python processor is implemented and independently reviewed. The existing Pi/FRC service uses it. Native C# portability and finer adaptive scanning remain explicit future work.

Scope and verdict

Approve this first modularization phase. Reviewed the working-tree changes on master based on a039b2b, including the new processing module, embedding documentation, tests, solver interface, and service integration. No native library, C# binding, camera SDK, or adaptive rake is represented as implemented.

A read-only Terra design critique supported the frame-in/results-out seam, geometry-only inputs, and explicit distinction between Python reuse and cross-language portability. A separate Sol reviewer inspected the implementation and tests, found a yaw-timing regression, and approved the revised implementation after re-review. No unresolved blocking findings remain.

What changed

  • VisionProcessor.process accepts caller-owned images and seconds-based timestamps. Detection-only needs no profile or calibration. Existing CameraCalibration plus tag size enables metric solving; field layouts are optional.
  • FiducialDetector is a structural interface, so a replacement implementation does not inherit from the OpenCV detector. Detector adapters own ROI strategy and must preserve IDs and decoded corner orientation.
  • Solver input types no longer import capture configuration or transport modules. The processor imports no capture, profile, output, recording, or NetworkTables modules.
  • The existing service retains capture, reconnect, output, recording, display, FPS/frame age, robot mount, and yaw/trig augmentation. The processing path is shared with direct embedding consumers.

Review finding resolved

The first extraction moved yaw lookup before detection. Since the yaw source polls incoming samples when queried, this could exclude an after-capture sample delivered during detection and lose interpolation. Robot-specific augmentation now lives in the service after image processing. A deterministic test supplies yaw at 9.99 s, captures at 10 s, and delivers the 10.01 s sample from the detector; interpolation is retained.

The regression test was explicitly run against the incorrect early-lookup order and failed, then passed after restoring the corrected order. A same-second, equal-size source restoration required removing the generated service bytecode cache before re-running; the final full suite ran against the corrected source.

Limits and next phase

Existing OpenCV/WPILib coordinate conventions remain explicit. A host must adapt SDK pixel formats and world coordinates. The archived custom decoder is not yet a calibrated main-pipeline backend; its adapter must preserve decoded corner orientation before adoption.

No native/C# or target-camera runtime was built or tested. The companion plan proposes one C/C++ core and a versioned C ABI with Python and C# bindings, rather than a separate implementation for every device. Recursive finer scanning remains an opt-in experimental direction to justify against recall and latency on a representative corpus.

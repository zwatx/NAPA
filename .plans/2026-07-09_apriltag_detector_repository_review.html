The 0.3.0 hardening implementation now has bounded capture/recording boundaries, robust pose diagnostics, timestamp-aligned yaw, replay gates, and verified distribution artifacts; remaining risk is physical evidence and release ownership.

Follow-up verdict. The locally actionable findings were implemented and independently re-audited through 39f04c9. The code and 0.3.0 artifacts are suitable for replay and controlled bench testing. Do not treat the bundled calibration/layout as competition-ready or publish until a redistribution license and release metadata exist.

Review scope

This review covered the full Python runtime, profiles, tests, output contracts, build metadata, CI, documentation, generated artifacts, and the repository-only occlusion experiment. It compared the NetworkTables packet with the 2026 upstream Mechanical Advantage Northstar publisher and robot consumer. The review began against an unborn master working tree; the accepted snapshot was subsequently recorded as commit 9a345a8. The repository now targets github.com/Zw96042/apriltag-detector.

The initial baseline had 8 passing and 3 failing tests under current OpenCV, profiles that disappeared from installed wheels, deprecated ArUco calls, mixed coordinate conventions, ambiguous output semantics, epoch timestamps on a monotonic NetworkTables contract, and no supported CLI/package boundary.

Verification

  • ruff format --check . and ruff check . pass.
  • 100 tests pass on Python 3.11 / OpenCV 4.7 / NTCore with 76.92% branch coverage; 96 pass and one NT-gated module skips on Python 3.14 / OpenCV 5 with 76.60% coverage.
  • Four real local NTCore integration tests cover yaw timestamp interpolation, producer duplicate suppression, observation capture timestamps, identical latest-value delivery, and final-update drain.
  • The 0.3.0 wheel and source distribution build cleanly, pass twine check, contain all intended commands/resources, install in isolated environments, and validate bundled profiles outside the repository.
  • Not verified: a physical camera, Raspberry Pi sustained load, live roboRIO time synchronization, actual camera calibration, or official field measurements.

Open decisions

  • Choose the redistribution license and repository remote before any public release.
  • Choose whether the deployed profile preserves upstream lossless sendAll behavior or prioritizes latest-pose latency after live radio testing.
  • Choose the target Raspberry Pi model, OS image, camera backend, pixel format, and performance budget for the production gate.
  • Ensure robot-side yaw publishing preserves duplicate stationary samples or carries an explicit heartbeat.
